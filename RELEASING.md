# Releasing

Only RSI Tech maintainers publish releases.

## Common release gate

1. Confirm the version is an honest maturity label and matches the intended tag.
2. Run the complete validation block in [`CONTRIBUTING.md`](CONTRIBUTING.md).
3. Resolve or explicitly accept dependency, license, vulnerability, public-API,
   recording-format, protobuf-wire, FFI-ABI, and performance-regression findings.
4. Build twice from clean directories at the exact reviewed commit and require
   identical binaries, archives, SBOMs, and checksums for each target.
5. Inspect the archive, SBOM reference closure, checksums, license, notice,
   migration notes, and binary `version`/`--help` output.
6. Merge through a reviewed pull request; rebuild from the exact `main` commit.
7. Archive an evidence manifest containing the commit, tag, toolchain, runner
   image, target triples, input hashes, output hashes, and gate results.
8. Tag only that commit. Let the release workflow build and attest artifacts;
   publication remains a separate maintainer-approved action.
9. Verify an anonymous clone, direct download, checksum, extraction, binary
   smoke, SBOM subject, and `gh attestation verify` for every published asset.
10. Update [`docs/plan/spec_conformance.md`](docs/plan/spec_conformance.md) with
    the exact receipt; do not infer operational proof from a green build.

## Maturity-specific gates

- **Alpha:** repository tests and release tooling are green; limitations are
  explicit; artifacts are prereleases.
- **Beta:** every claimed beta adapter/channel has discovery and deterministic
  replay evidence plus at least seven consecutive calendar-spaced scheduled
  canaries. No unresolved high-severity correctness or security finding.
- **Stable:** beta gates plus at least a seven-day Linux live soak, complete
  stable-channel coverage, named adapter/operations owners, dashboards,
  runbooks, migration notes, and release-profile chaos/recovery evidence.
- **1.0 / production-ready claim:** at least two stable adapters, external
  public-API review, Linux x86_64 and aarch64 artifacts, verified provenance,
  compatibility receipts for supported recording/protobuf/FFI contracts, and
  explicit maintainer sign-off against the production specification.

The tag must be `v` followed by the Cargo workspace version. Do not move an
existing release tag. Mark alpha and release-candidate versions as GitHub
prereleases.

## Local package

```bash
./scripts/package-release.sh
```

The script builds the portable Cargo `release` profile for the current host and
writes a target-qualified versioned archive, CycloneDX SBOM, and
`SHA256SUMS-<target>` plus `EVIDENCE-MANIFEST-<target>.txt` under `dist/`.
The manifest records the exact source, toolchain, runner identity, target,
input/output hashes, and local packaging gate results. Published filenames must
match the files generated by the script; target qualification prevents
cross-platform release assets from colliding.

The current downloadable binary target is Apple Silicon macOS only. Do not
claim Linux, Intel macOS, Windows, Developer ID signing, notarization, or
provenance until those exact artifacts and controls are published and
independently verified.

## Rollback

If consumer verification fails, leave the repository available, mark the
release affected, remove misleading download references, and publish a fixed
version. Never retag a different commit under an existing version.
