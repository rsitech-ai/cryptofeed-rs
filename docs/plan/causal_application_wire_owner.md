# MFCJ5 application-write owner protocol

This is an opt-in public Hyperliquid spot/perpetual disk/null native-owner protocol. It adds application Text/Binary write authority to the existing actual native owner, typed history validator, native replay and MFOP1 projection. It does not supply a live transport driver, CLI activation, availability-time authority or consumer qualification.

MFCJ5 negotiates before the watermark. Its Bootstrap contains the canonical, hash-bound `hyperliquid-application-wire-v1` role plus the existing native observation and history policies. OwnerHistory schema4 requires Operation schema2. MFCJ1..4 keep their original schemas and cannot admit this role. Runtime HTTP, private/non-Hyperliquid factories, dynamic catalog changes and allMids remain unsupported. Application Stop/Resync and all accepted inputs remain journaled; the explicit `ManagedConnectReadAutomaticPongCloseUnjournaledV1` disposition covers only transport-managed connection/read/automatic Pong/close. Native protocol-control drain entries remain exact source evidence but are not duplicate sends. Scheduled Hyperliquid JSON text pings are application writes and require authorization.

The owner derives one bounded write bundle only from an actual native-matched eligible HandoffObserved after its actor ACK. Every candidate binds the original input, native route, execution-completion and handoff journal ordinals, physical connection, native frame sequence, original input FrameStamp (when present), exact complete-drain position and exact opcode/payload. New native execution waits for this bundle; safety ingress still changes the fence synchronously. Native input and wire-bundle limits are separate bounded reservations. Source retention reports their combined counts/bytes; candidate bytes conservatively reserve base64 payload bytes plus1024 identity bytes each. A staged ledger, decoded outbound frame, actor preparation and caller-owned native results add temporary bounded copies, not a process RSS guarantee.

`HistoryJournalOwner::try_take_wire` returns a noncloneable opaque `WireAuthorization` only after a real WireIntent actor ACK. It exposes an ID, not a raw frame or caller-supplied receipt/success API. `WireAuthorization::invoke(&mut impl WebSocketTransport)` journals InvocationPermitted, waits for its actor ACK, then rechecks current connection/fence/deadline. Both the actual write_frame method call and first Future poll occur under that fresh fence lock. A transport must not synchronously reenter this owner from either; the driver must own the corresponding physical socket. The transport trait cannot prove remote socket identity. Blocking method calls/polls, in-flight I/O and accepted writer tickets can make shutdown/join unbounded.

Actual return values become journaled Succeeded or Failed with exact typed transport errors up to4096 UTF8 bytes. A larger error becomes explicit Unknown capacity evidence with category, original byte length and SHA256; it is not truncated or treated as safely retryable. Cancel/drop after invocation may have begun records Unknown. Known complete results are retained even if their caller disappears while waiting for the result ACK. Observed Failed/Unknown immediately fences snapshots and new ingress before its result ACK; the exact result remains queued through ordered Revoked/finalization records and healthy Full retries. No failed/unknown effect can be retried or become clean by reconnecting. Uninvoked fenced/expired leases settle NotInvoked; remaining old candidates retire without new authority. A new physical connection cannot revive an old token. Stop before invocation prevents it; Stop after invocation cannot claim bytes were unsent.

Only exact post-barrier wire result receipts are returned to the caller. A source prefix ending at intent/invocation remains explicitly uncertain. Native replay re-derives bindings from actual completed operations and rejects CRC-valid substituted payloads. Source and projection validators reject every new native execution permit while the wire bundle is pending or permanently uncertain, including after a Failed/Unknown result empties it; ingress/safety evidence remains recordable. MFOP1 retains the typed wire controls, exact clock/lineage and pending state; its standalone reader is structural, with actual source comparison required for financial/source authenticity. Generic storage writers can physically append a Seal, but typed owner replay and projection refuse a Seal with pending or permanently uncertain wire effects. A driver must separately prove actual intentional Stop settlement/lifecycle and its own source/target shutdown, rather than treating wire_clean alone as all-owner completion.
